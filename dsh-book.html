零基础起步：一个 agent 到底是什么

来源：仓库 README.zh.md、docs/cordis-primer.zh.md、packages/llm/llm/src/types.ts、packages/llm/token-meter/src/estimate.ts、packages/core/tools/src/index.ts（本地克隆核对）

学完这一章你应该能做到

  • 用自己的话解释「大语言模型没有记忆」的确切含义，以及它为什么逼出后面十几章的所有设计
  • 估算一段中文大约值多少 token，说清 token 上限为什么是硬约束
  • 把「工具调用」拆成四步，指出哪一步是 AI 干的、哪三步不是
  • 亲手单步走一遍二十行的最小 agent，并用一条可验证的判据确认它跑对了

0.1先说清楚：没有 agent 的时候，人是怎么干活的

你想让 AI 帮你改一个叫 report.txt 的文件。2023 年的干法：打开聊天窗口，手动把文件内容复制进去，问它怎么改，它给你一段新文字，你再手动复制回文件。每一次「复制、粘贴、切窗口」，都是你在当搬运工。

你干的活其实特别机械：把外面世界的东西喂给模型，再把模型说的话拿到外面世界去执行。既然机械，就能写成程序。这个程序就是 agent 的全部。

定义 agent（智能体）：一个能自己循环调用模型、并且能真的动手（读写文件、执行命令、访问网络）的程序。它不是一个模型，是一个围着模型转的程序。
harness（智能体运行框架）：承载 agent 的那一层框架。DeepSeek Harness 的 README 第一句就是这么自我介绍的。模型是马，harness 是马身上那套挽具。
一句话记住：agent 里最难的部分没有 AI。AI 只负责「说下一步该干什么」，剩下的全是普通程序的活儿——而恰恰是这些普通程序的活儿，撑起了 20 万行。

0.2大语言模型：一个吃文字吐文字的函数，而且它没有记忆

把模型当成一个函数：你给它一段文字，它还你一段文字。没有别的接口。它不能读文件、不能上网、不能执行命令、不能记住昨天你说过什么。

你在聊天软件里跟 AI 连聊十轮，感觉它记得你。真相是：聊天软件在第十轮时，把前面九轮的全部内容重新发了一遍。模型这一侧根本不知道有「第十轮」这回事。

rn = f(S, m₁, r₁, m₂, r₂, …, mₙ)          式 0-1
符号是什么直觉
f模型本身只会「接一段、续一段」的机器。纯函数：同一份输入进去，不依赖任何外部状态
S系统提示每次都要重发的开场白：你是谁、能用哪些工具、有什么规矩
mₖ第 k 轮用户说的话人打的字
rₖ第 k 轮模型的回复上一次它吐出来的那段文字，下一次要原样带回去

注意式 0-1 右边的括号：第 n 轮的输入包含前面所有轮的输入和输出。这就是「没有记忆」的精确写法——所谓记忆，是括号里那一长串，而它是你的程序负责保存和重发的。

打个比方 模型像一个每天早上彻底失忆的专家。要他接着昨天的工作干，唯一的办法是每天早上把昨天的完整工作日志重新念一遍给他听。
⚠ 类比失效处：失忆的人至少知道「我失忆了」，模型连这个都没有——它不是忘了，是压根没有「上一次」这个概念。而且真人听同一份日志两次会给同样的回答，模型不一定：输出带随机采样，严格说 f 是带随机性的函数，式 0-1 是简化写法。
常见误解❌ 「模型能记住 128K 上下文」= 模型自己存了 128K 记忆。不是。那个数字是单次输入的长度上限——上限之内的东西，仍然要你每次原样重发。

这一条会在后面变成两整章：① 对话要整段重发 ⇒ 这份「整段」必须被完整可靠地存下来 ⇒ 会话日志（第 6 章，仓库把它写成运行时不变量「模型可见即已记录」）；② 单次长度有上限 ⇒ 对话总有一天塞不下 ⇒ 压缩（第 12 章）。

0.3token：为什么按字算钱，为什么装不下

东西大约多少 token可感知的比较
一个汉字0.5 ~ 1——
一条微信消息（30 字）20 ~ 30——
一篇公众号推文（3000 字）2000 ~ 3000——
一本 20 万字的中文书12 万 ~ 20 万比绝大多数模型单次能吃下的还多
一个 500 行的代码文件4000 ~ 8000agent 读一次文件就是这个开销
dsh 的全部中文文档约 75 万 ~ 120 万105 篇文档、共 123 万字符
读的时候要小心 · 本站给的量级上表换算是量级参考，不是仓库数据也不是任何模型的官方 tokenizer 结果。网上「1 个汉字 = 2 个 token」多是老模型经验值，别当常数用。

单次上限是多少？这个数不在仓库里——它是模型目录的可选字段 contextWindow（packages/llm/llm-deepseek/src/index.ts，注释：「部署元数据不可用时省略」）。harness 自己不假定这个数，由你接的模型告诉它。

有意思的是，dsh 自己也不精确数 token。本地仓库 packages/llm/token-meter/src/estimate.ts:13：

const CHARS_PER_TOKEN = 4   // 固定文本密度估计，直到拿到精确 tokenization
const BLOCK_OVERHEAD = 4   // 每个内容块的 JSON 结构开销

四个字符算一个 token——这是故意粗糙的兜底：一旦提供方返回真实 usage，就改用真实值当锚点。但这条常数对中文是系统性低估（4 个汉字算 1 个 token，实际约 1–2 个汉字就 1 个 token），所以用中文跑 dsh 时压力估计偏乐观。仓库没有讨论这一点，这是本站读源码时注意到的。

把 0.2 和 0.3 拼起来，得到一个不太好的结论。设每轮新增量约为常数 c，则聊到第 n 轮的累计发送量：

T(n) = ∑ₖ₌₁ⁿ k·c = c · n(n+1)/2          式 0-2

关键是 n²：轮数翻一倍，花的钱变四倍。10 轮对话的成本是 1 轮的 55 倍，而不是 10 倍。

读的时候要小心 · 本站推导式 0-2 仓库里没有；且假设「每轮新增是常数」，真实工具结果大小差异巨大（读一个大文件可能一次吃掉一半预算），真实曲线比 n² 更不平滑。只用来说明「为什么平方增长」，不能拿去算真实账单。

0.4工具调用：全站的地基

到这里为止，模型还是只会说话。你问「目录里有几个文件」，它只能猜或编；你说「帮我把这行删了」，它回一句「好的，已删除」——文件一个字节都没变。工具调用就是在「模型说的话」和「现实」这堵墙上开的那扇门。

很多人以为「模型调用工具」是模型内部长出了一双手。错，而且错得重要。真实机制是四步：

你的程序（harness）
保存整段对话
解析工具调用
真的执行 · 真的负责
模型
吃一段文字
吐一段文字
什么都碰不到
真实世界
文件 · 命令 · 网络
① 整段对话 + 工具清单
（清单本身也占 token）→ ② 一段文字
（可能含 tool-call）→ ③ 真的执行
（唯一改变世界的一步，零 AI）→ ④ 结果变成新文字
整段再发一遍（回到式 0-1）

这不是比喻，是仓库的类型定义（packages/llm/llm/src/types.ts:99）：

interface ContentBlockMap {
  'text':        TextBlock
  'reasoning':   ReasoningBlock
  'image':       ImageBlock
  'tool-call':   ToolCallBlock        // id + name + arguments（原始 JSON 文本）
  'tool-result': ToolResultBlock      // toolCallId（配对用）+ 结果内容 + isError
}

而「真的去执行」那一步（packages/core/tools/src/index.ts）：一个普通的 execute 函数，参数是模型给的 JSON，返回普通 JSON，里面写的是 fs.readFile 这种最普通的代码。dsh 一共注册了 52 个这样的工具：bash、read、write、edit、glob、grep、web_search、todo_write……名字都很朴素。

常见误解「模型自己执行了命令」——没有。模型输出了一串字，你的程序看见那串字，自己去执行。所以：工具能干的事，就是你允许它干的事。模型说「删除整个磁盘」和说「今天天气不错」在传输层面完全一样——会不会真的删，取决于你的程序里有没有那段代码、有没有拦。这就是第 9、10 章整两章权限问题的由来，而那两章从头到尾没有 AI 参与。
一句话记住：工具调用不是模型「获得了能力」，而是模型获得了请求你替它做事的语法。真正的能力一直在你手里，也一直是你的责任。

ToolResultBlock 里那个 toolCallId 字段为什么存在？——说明有时光靠顺序不够。
模型一次要读 a.txt 和 b.txt，你为了快并发执行、谁先返回先追加谁。顺序变成「调a、调b、b的内容、a的内容」，没有 id 模型只能按顺序猜——把 b 的内容当 a 的，拿着错误文件继续干，全程不报错，因为每步语法都合法。toolCallId 把「哪个结果对应哪个调用」从靠顺序变成靠标识。变式：强制串行且按模型顺序追加就安全了吗？想想「某个工具超时了、你决定跳过它」。

0.6依赖：为什么「谁先启动」会变成一个问题

二十行循环里没有这个问题——它只有一个文件。可一旦你的程序变成几百个插件（工具注册表要等工具都注册完，模型适配器要等配置读进来），「谁先启动」就成了问题。dsh 的答案：依赖不是排顺序，是声明需求。

// packages/core/agent-loop/src/index.ts（本地克隆核对）
export class AgentLoop extends Service implements AgentFactory {
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt']
}
定义inject：插件只声明「我需要这几个服务」，框架自己算启动顺序。没被满足的插件停在 PENDING——安静、合法、不报错，服务到位就启动。
常见误解❌ 「inject 里的服务不存在会报错。」不会，插件静默地永远等待。这是排障时最先该查的地方——推论：改配置文件的行序毫无作用，顺序由依赖图决定。

0.7状态机：几个格子，加上格子之间的箭头

为什么需要它：插件可能「加载中 / 等依赖 / 运行 / 卸载中 / 失败」，如果用一堆布尔标记（isLoading && !failed && …）组合会爆炸。状态机把「一堆标记的组合」压缩成有限几个合法状态。Cordis 的 fiber 有六个状态；dsh 的会话、终端、任务各有自己的状态机——出问题时先问「它现在在哪个格子、卡在哪条边上」。

PENDING
（等依赖）→ RUNNING→ DISPOSING
（卸载中）→ DISPOSED / FAILED

0.§机判自测（4 题）

答完自动计入你的进度。答得吃力就去复习区再过一遍。

L1 · 直接应用数值题
用 CHARS_PER_TOKEN = 4 估算：2000 个汉字（不计块开销）值多少 token？
2000 ÷ 4 = 500。注意真实值约 1000~2000（一个汉字 0.5~1 token），所以这条规则对中文低估 2~4 倍——harness 以为还很宽裕，实际已近上限，压缩会触发得太晚。
L2 · 变形迁移数值题
每步新增 c = 1500 token，整段重发，走完第 20 步的累计发送总量？（式 0-2）
T(20) = 1500 × 20×21/2 = 315,000。真实新内容只有 30,000——同样的信息付了约 10 倍。
L1 · 直接应用数值题
聊了 5 个来回后发第 6 句：这次请求总共包含几条消息（不含系统提示）？
用户消息 6 条 + 模型回复 5 条 = 11 条。模型自己说过的也要带回去——对这次请求而言，它上次说的话和你说过的一样，都只是输入文字。
L1 · 直接应用数值题
工具调用四步里，「真正改变世界」的是第几步？
第 ③ 步——你的程序真的去执行。那一步零 AI 参与，也是全部责任的所在。

0.∞本章小结

六件事：一，模型是无状态函数，你每次整段重发（式 0-1），记忆是你的程序在维护；二，token 同时是钱和硬上限，累计成本随轮数平方增长（式 0-2）；三，工具调用是「模型请你替它做事的语法」，执行和责任都在你的程序——全站地基；四，JS 六样东西；五，依赖是声明不是排序，没人提供的服务让插件静默等待；六，状态机把布尔组合爆炸压成有限格子。

你已经单步走过了那个 20 行循环。它对应 dsh 的 packages/core/agent-loop（本地克隆 6 个源文件、1691 行）。从 20 行到 1691 行中间在干什么？整个仓库剩下的 20 万行又在干什么？第 1 章一条一条告诉你，你那 20 行在真实世界里会怎么死。

上下文与服务：为什么不用 import

2.1import 把两个决定焊死了

import { bash } 把「我需要什么」和「谁来满足我」写死在同一行。而这两个决定本该由不同的人在不同时刻做出。ctx 是一个装服务的容器：消费方只说名字（ctx.llm），不说实现。

定义PENDING：声明的依赖尚未就绪时插件停留的状态。依赖齐了才跑 apply。依赖不是启动时查一次，是一直盯着：服务消失，依赖它的插件跟着卸载；服务回来，再加载。这条性质让「从配置换掉任何实现」成为可能。

两件小事：可选依赖用 ctx.get(name) 探测（不进 PENDING，但提供方重载期间返回 undefined）；服务名是一张全局平表，撞名让后登记者进 FAILED——仓库靠加前缀的约定缓解，没有强制机制。

自己算一遍：换一家模型厂商要动几个地方？
零个代码文件。写一条 patch 把 id: llm 那行的 name 换成另一个适配器包，配置好 provider——依赖 llm 的所有插件自动经历一次「卸载→重挂」。前提：新适配器实现同一个消息/流词汇表（ContentBlockMap）。

副作用为什么必须可逆

3.1不可逆注册留下的现场

插件注册工具后若不可撤销，热重载之后旧注册不是被替换而是被叠加：工具表多一条指向死代码的记录、事件上多一个幽灵监听器、多一个没人管的定时器——且没有任何报错。这类 bug 和操作历史绑定、不和代码绑定，复现不出来也就修不掉。

定义ctx.effect()：拿资源的时候，就把「还回去」的办法交给框架。插件做的一切都记为一条效果；卸载时逆着启动顺序、并发地展开。dispose 会递归，而且会等。
热重载不是专门实现的功能，是「一切注册皆可逆」的自然推论——vendor/hmr 只是把推论工程化。
打个比方ctx 像酒店服务台：不是把电器焊死在墙里（import），而是打电话叫服务（ctx.xxx）；退房（卸载）时你叫过的所有服务被自动撤掉。
⚠ 类比失效处：酒店服务彼此独立；ctx 的注册有顺序，卸载按启动的逆序进行。
自己推一遍：效果不可逆时 HMR 会出什么事？
幽灵注册：新旧两份同时响应同一事件，行为不可预测。可逆效果保证旧作用域整体销毁后再挂新的。你推到「重复注册」这步就及格。
真未解一个永远不结束的释放函数该由谁兜底？进程内框架没有操作系统那种强杀手段。

会话日志：模型可见即已记录

6.1一个消息数组，五件它做不到的事

消息数组存的是状态；撤销、fork、回放、崩溃恢复、记账问的全是过程。所以换成仅追加日志：只往末尾加，从不修改已有条目——写入点用深冻结和 JSON 校验把它做成结构上的不可能。

模型历史不是存着的，是从日志投影出来的（deriveMessages()）。同一份日志还投影出人类界面、账单、UI 状态——它们互不打架，因为都从同一个真源算。

6.2那条会被代码检查的规矩（本地克隆核对）

铁律模型可见即已记录。packages/core/agent-loop/src/invariant.ts 会在请求发出前核对「即将发出的请求」与「从日志重放的推导」一致，不一致直接 fail：llm request … diverges from the dispatch-time durable derivation (log-reconstruction desync)。推论：想给模型加一种新输入，就必须新增一个会话事件类型并从日志渲染，没有第二条路。

13 种事件里只有 3 种产生模型可见内容（user/message、assistant/message、tool/result），且必须在写入时声明怎么加入 surface：追加，或替换掉一段（压缩用）。被替换的事件仍留在日志里，只是模型看不见了。fork、恢复、崩溃修复共用同一个机制：拿一段事件流当种子；崩溃后补一条合成的 interrupted，而不是截断日志。

轮次与步骤：循环真正的样子

7.1三个不能混的词

步骤= 一次模型请求 + 它调用的工具；轮次= 零个或多个步骤，在领取首条输入之前打开、不再欠工作时关闭；Round= 外层策略的计数。「零个步骤的轮次」必须存在：被拒绝的输入仍要留下一条持久记录——日志必须记录这次尝试。

7.2完整流水线（仓库明文）

inbox/claim→ turn/start→ agent/pre-step 🔶→ user/message 入日志→ deriveMessages()→ agent/request 🔶→ llm/stream 🔶→ assistant/message→ tool/call*
先记账再执行→ tools/pre-execute 🔶→ 审批 + 守卫
(第 9–10 章)→ tools/execute 🔶→ tools/post-execute 🔶→ tool/result
按模型顺序提交→ step/end（finally）→ agent/turn-stopping 🔶→ turn/end

🔶 = waterfall 瀑布事件：监听者包裹 next() 形成洋葱，必须调用 next()。

三条贯穿全书的纪律：① 宁可记了没做，不能做了没记；② 模型可见即已记录；③ 记录顺序按模型顺序，不按完成顺序。

权限：只许说不，不许说是

10.1黑名单是错的答案

枚举坏的，失败方向是放行；枚举好的，失败方向是拒绝。安全边界必须选后者。dsh 把这条做到类型层面：

定义单调守卫：ToolGuard 的返回类型是 string | undefined——没有 allow 分支。任意多个守卫叠加的结果是交集，只会更严不会更松，且与注册顺序无关。删掉 allow 分支，等于让「谁的允许盖过谁的拒绝」这一整类 bug 在类型层面不存在。

默认拒绝：没装审批服务、没有应答者、应答者抛异常、返回值不在词汇表里——四种「答不上来」全部倒向拒绝。ApprovalOutcome 里只有 allowed-once 是许可，且只授权所询问的那一次。第二堵墙——沙箱：守卫决定要不要做，沙箱决定做了能跑多远（Landlock 限制文件系统效果，不管网络）。

五件不牢靠的事（设计使然）① isConcurrencySafe 是工具的自我声明，无人校验；② timeoutMs 只是声明，不装策略包就没有超时；③ fs 单槽归属是部署约定不是强制不变式；④ 被拒绝的调用不走守卫；⑤ never 的判定在 waterfall 之前——prepend 的监听器抢不到它前面。

这套设计欠了什么债

债是决策的背面，不是缺陷。想去掉右边，就得放弃左边同一行。

决策（买到的）债（付出的）
一切皆插件 → 任何部分可替换没有入口；能力散在三个包；启动失败 = 静默 PENDING
仅追加日志 → 恢复、回放、审计磁盘只增不减
单调守卫 → 组合安全放宽策略无法用插件表达
waterfall → 极强拦截能力忘调 next() 是静默失败

复习 · 间隔抽认

每次只揭一层提示；用到第几层，就说明第几层还没长进脑子里。

Q1「模型能记住 128K 上下文」这句话哪里错了？
那个数字是什么的上限？
上限之内的内容，每次要不要重发？
128K 是单次输入的长度上限，不是模型自带的记忆。上限之内的内容仍然要每次原样重发——记忆是括号里那一长串（式 0-1），由你的程序维护。
Q2工具调用四步里哪步是 AI？为什么说「工具能干的事就是你允许它干的事」？
只有一步发生在模型那一侧。
只有 ②（输出 tool-call 块）是 AI；①③④都是普通编程。模型说「删除整个磁盘」和说「今天天气不错」在传输层面完全一样——会不会真删取决于你的程序里有没有那段代码、有没有拦。这是第 9、10 章的由来。
Q3为什么多个守卫叠加只会更严、不会更松？
看 ToolGuard 的返回类型。
string | undefined——里面没有 allow。
类型层面不存在「放行」分支，叠加结果是各拒绝条件的交集，与顺序无关。「谁的允许盖过谁的拒绝」整类 bug 在类型上不可能发生。
Q4四层 patch 的顺序？打不中会怎样？
bundle → profile → home → 命令行；后写胜出。
打不中只写 stderr 警告、不报错——装配层唯一的「静默」。对策：dsh --profile web --dump-config 打印最终树。注意 patch 替换整个 config、不做深度合并。
Q5为什么压缩不违反「从不修改日志」？
被压掉的事件去哪了？
surface 的两种加入方式：追加 / 替换一段。
摘要作为新的替换型 surface 事件写入日志，被替换的原事件仍留在日志里，只是不再投影给模型。「模型看不见 ≠ 没发生过」——审计和回放不受影响。

使用速查

# 最快上手（npm，需 Node ≥22.19）
npx @deepseek-ai/dsh web            # 打开 http://127.0.0.1:3080
npx @deepseek-ai/dsh web --no-open  # SSH 场景，不开浏览器

# 从源码（本仓库）
pnpm install && pnpm run build && pnpm dsh web
pnpm run typecheck                  # 成功退出 = 环境搭好了

# 排障第一工具：打印组合后的插件树
dsh --profile web --dump-config

# 其他形态
dsh --profile headless ...          # 无服务器一次性执行
dsh --profile acp                   # 编辑器自动化（ACP）
dsh plugin ...                      # 安装树外插件

# 模型配置
#   推荐：Web UI → Settings → Models 填 DeepSeek API Key
#   环境变量：DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL
#   Key 只写存于 $DSH_HOME/.credentials.yaml
#   自定义 OpenAI 兼容供应商：settings.yaml 的 llm-pi-ai.providers
安全须知（仓库明文）开发者预览，会有破坏性变更（SAFETY.md）。Web 服务器无内置 TLS/鉴权，只绑 127.0.0.1——不要暴露到不受信网络。会话格式版本停在 0，无兼容承诺。生产使用开启沙箱/审批（packages/guard，Linux 配合 native/landlock-run）。
