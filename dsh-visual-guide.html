0.1模型是个无状态函数

每次调用 LLM，你都把完整历史发过去，它返回下一段输出。它不记得上一轮——"记忆"是你（调用方）每次重放历史实现的。这就是为什么 dsh 要有一个 packages/core/session：一份追加式的 SessionEvent 日志，每轮用 deriveMessages() 从日志推导出消息列表。口诀：模型可见即可被记录。

打个比方 LLM 像一个每 5 秒失忆一次的专家：你要持续请教，就必须每次把聊天记录完整打印一份递给他。SessionEvent 日志就是那份聊天记录的"账本"。
⚠ 类比失效处：真人专家会自己积累经验，而 LLM 连"上一秒说了什么"都依赖你重放——上下文窗口满了就需要 compaction（压缩）插件来裁剪历史。

0.2一次工具调用的 4 步

① 程序把工具 schema
随消息发给模型→ ② 模型返回结构化
"我要调 bash(command)"→ ③ 程序真正执行命令
拿到真实世界的结果→ ④ 结果作为 tool 消息
追加进历史，再次请求模型

把 ②→④ 套进循环，就是最小 agent。整个 dsh 的 agent-loop 包只占全仓库代码的 0.89%——剩下 99% 都是在让这个循环变得可靠、可观测、可插拔。

常见误解 ❌ "是模型自己去执行了 bash 命令。" —— 模型只输出了一段结构化的请求文本；执行永远发生在你的程序里，这就是 harness 存在的理由。
动手 · 20 行最小 agent 用任何 OpenAI 兼容 API 写一个循环：发消息 + 一个 echo 工具 → 收到工具调用就执行 → 把结果拼回消息再发。做对了的样子：模型连续调用工具两次以上仍不混乱，历史完整重放。 
while (true) {
  const res = await callLLM(messages, tools)      // ①②
  if (!res.toolCalls) break                        // 没有工具调用 → 结束
  for (const call of res.toolCalls) {
    const result = await execute(call)             // ③
    messages.push(toolResult(call, result))        // ④
  }
}

packages/core/scope · 为什么是 ctx.llm 而不是 import。

2.1插件的样子

每个包导出一个类（常继承 Service）或 apply(ctx) 函数；static inject 声明依赖的服务键，框架保证依赖就绪后才启动。仓库原文（packages/core/agent-loop/src/index.ts:296）：

export class AgentLoop extends Service implements AgentFactory {
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt']
  // create()/resume() 发布 ReactLoopAgent 句柄；卸载时效果自动回滚
}
export default AgentLoop
定义 ctx（Context）：每个插件拿到的是一个作用域化的上下文（packages/core/scope），插件在它上面注册的服务、事件、效果都是可逆的——插件卸载时全部自动撤销。对比 import：import 是编译期强耦合且不可撤销；ctx 是运行期、按需、可拆卸的服务查找。
打个比方 ctx 像酒店的客房服务台：你不是把电器焊死在墙里（import），而是打电话叫（ctx.xxx）；退房（插件卸载）时，你叫过的所有服务会被自动撤掉。
⚠ 类比失效处：酒店服务是并发的、彼此独立；而 ctx 上的注册有顺序，卸载按启动的逆序进行（见第 3 章）。

可逆效果：为什么热重载是"推论"不是"功能"

ctx.effect() · 卸载顺序 · HMR。

3.1效果即注册

插件做的每件事（注册工具、监听事件、启动终端）都被记为一条效果（effect）。卸载时框架逆着启动顺序、并发地展开这些效果。因为注册天生可逆，"改了插件配置后热重载"不需要专门实现——它是可逆性的自然推论（vendor/hmr 只是把这个推论工程化）。

自己推一遍：如果效果不可逆，HMR 会出什么事？
会出现"幽灵注册"：旧版本插件注册的工具/事件监听还挂在 ctx 上，新旧两份同时响应，行为不可预测。可逆效果保证旧作用域整体销毁后再挂新作用域。想好了再对照：你推到"重复注册"这一步就及格了。

Agent 循环：一轮对话的完整流水线

packages/core/agent-loop · ReactLoopAgent。一个 step = 一次模型请求 + 其工具调用；一个 turn = 若干 step。

学完这一章你应该能做到

  • 按顺序默写 turn 流水线
  • 指出哪些是瀑布事件、为什么必须 next()

4.1流水线（仓库明文）

turn/start→ agent/pre-step 🔶→ step/start→ 追加用户消息→ deriveMessages()→ agent/request 🔶→ llm/stream 🔶→ assistant/chunk*→ tool/call*→ tools/pre-execute 🔶→ tools/execute 🔶→ tools/post-execute 🔶→ tool/result→ step/end→ agent/turn-stopping 🔶→ turn/end

🔶 = 瀑布（waterfall）事件：监听者包裹 next() 形成洋葱层，必须调用 next() 才能继续。

定义 洋葱模型：瀑布事件的每个监听者都可以在 await next() 之前/之后插入逻辑——之前改参数、之后改结果。审批插件在 tools/pre-execute 的 next() 之前拦截危险命令，压缩插件在 llm/stream 的 next() 之前裁剪消息。

4.2一个工具的完整定义

工具用 defineTool()（packages/core/tools/src/schema.ts:545）定义，以 bash 为例（节选自 packages/shell/tool-bash/src/index.ts:242）：

ctx.tools.register(defineTool({
  name: 'bash',
  description: bashDescription(backgroundEnabled, escalationModes),
  parameters: {
    command: { type: 'string', required: true, description: 'The bash command to execute.' },
  },
  output: { schema: { oneOf: [...] }, render(args, value) { /* UI 呈现 */ } },
  async execute(args, exec) { /* 走 ctx.shell 接缝，而非直接 spawn */ },
}))

注意两点：参数 schema 是类型化 DSL，编译成 JSON Schema 给模型看；execute 里只碰 ctx.shell 接缝——换成沙箱后端时工具零改动。

Q1为什么 agent/request 必须是瀑布事件，而不能是普通广播？
想想"修改即将发出去的消息"和"得知消息发出去了"的区别。
压缩插件需要改写请求内容（裁剪历史），广播事件只能旁观、不能替换载荷。
瀑布事件把"下一步"作为 next() 交给监听者，监听者可以换掉传给 next() 的参数。
瀑布事件形成洋葱：每个监听者包裹 next()，可以在调用前修改 messages/options（压缩、注入上下文），在调用后修改流结果（脱敏、计量）。普通 emit 无法把修改传回主流程。变式：tools/execute 为什么也是瀑布？（审批拒绝 = 不调用 next()。）
